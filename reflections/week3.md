# Task 1 — Change Impact Tracing

### Q1. Waterfall Process
The new multi-restaurant checkout feature would require:
- Updating the requirements and getting client sign-off again.
- Updating the system design and obtaining approval.
- Reworking completed UI, order data, payment logic and kitchen notifications.
- Additional testing and regression testing.
- Potential delays to the Month 5 testing and Month 6 go-live.

### Q2. 2-Week Increments
The change could be added to the backlog and prioritised for a future 2-week increment. The feature would be broken into smaller tasks, developed and tested within the increment, with client feedback incorporated throughout.

### Q3. Comparison

| Waterfall | 2-Week Increments |
|---|---|
| Requirements and design need revisiting | Change added to backlog |
| Rework of completed components | More contained changes |
| Repeated sign-offs | Prioritised between increments |
| Additional/regression testing | Testing within the increment |
| Higher schedule risk | Easier to manage change |

### Q4. Cost/Effort
The 2-week incremental approach would have a lower change impact. The feature is still complex, but agile allows it to be prioritised and incorporated into future work rather than requiring major changes to previously completed project stages. Waterfall would involve more rework, approvals, testing and schedule disruption.

**Conclusion:** Agile/incremental development handles mid-project change more efficiently than the waterfall approach.

# Task 2 — Process Diagnosis

| Weakness | Diagnosis | Improvement | Priority |
|---|---|---|---|
| Verbal requirements with no shared document | **No process** — requirements can be misunderstood. | Use simple written requirements/user stories. | **Must** |
| Direct pushes to main with no review | **No process** — errors may reach production. | Require one developer review before merging. | **Should** |
| Developer tests their own work once | **Weak process** — problems may be missed. | Use a simple testing checklist before release. | **Should** |

**Overall:** QuickBuild does not have too much process; it has **too little** process. Lightweight practices can improve requirements, code quality and testing without adding unnecessary bureaucracy.
